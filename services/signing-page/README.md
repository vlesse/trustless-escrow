# 签名页

用户点开 Telegram 里的签名链接后看到的页面。把机器人编码好的交易翻译成人话，验证它确实指向本协议的合约，然后交给用户自己的钱包去签。

**纯静态。没有后端。**

## 三条不能妥协的原则

### 1. 交易内容走 URL 的 `#` 片段，不走 `?` 查询串

fragment 不会被浏览器发送给服务器，也不进 access log。托管这个页面的一方——包括运营者自己——看不到任何人在签什么。

### 2. 解不出来就不放行

一个只会说"请签名"的签名页，是在训练用户盲签。**用户越习惯于看不懂就点确认，越容易在真正的钓鱼弹窗上点确认。**

所以页面会把 calldata 解码成具体的一句话（"确认收货并放款给卖家 · 货款立即放给卖家，此操作不可撤销"），解不出来就显示"无法识别的操作"并禁用签名按钮。

### 3. 目标合约必须经链上验证

任何人都能伪造一个签名链接。页面独立连 RPC 确认 `to` 是工厂登记过的托管实例；`approve` 则确认被授权方（spender）是。验不过就拒绝。

## 安全核验清单

每次打开都会跑，任何一项不过就阻止签名：

| 核验 | 拦住的攻击 |
|---|---|
| 不附带 ETH | 有人在原交易上加了 `value`。本协议所有操作都不需要发送原生币 |
| calldata 可解码 | 无法确认含义的调用，可能是伪造的 |
| 目标是工厂登记的托管合约 | 钓鱼合约地址 |
| 被授权方是工厂登记的托管合约 | `approve` 把代币划转权交给陌生合约 |
| 授权额度不超过交易所需 | 诱导无限授权 |

## 依赖是 vendor 进来的，不走 CDN

`vendor/ethers.umd.min.js` 随页面一同分发。这个页面授权转账，**CDN 被投毒等于所有用户被搬空**——SRI 能缓解，但不如彻底不依赖。`vendor/VERSION.txt` 记录了版本与 sha384，可自行比对。

## 部署

1. 编辑 `config.js`，填入每条链的 `factory` 地址、RPC、区块浏览器
2. 把整个目录丢到任意静态托管（GitHub Pages / Cloudflare Pages / IPFS）
3. 把该 URL 填进机器人的 `SIGNING_PAGE_URL`

`factory` 留空或填错时，页面会**拒绝签名**而不是放行——宁可不可用，也不能让用户在未经验证的合约上点确认。

本地调试：

```bash
node serve.cjs   # http://127.0.0.1:8788
```

## 这个页面不是必需的

机器人在每条操作消息里都同时给出原始的合约地址与 `calldata`。签名页挂了、被墙了、甚至运营者跑路了，用户都能把那两行东西粘进任何钱包完成操作。

**用户的资金不应当依赖这个页面存活。** 它只负责把体验从"能用"提升到"好用"。

## 验证情况

在本地链上对真实部署的合约跑过全部五种场景：

- 正常提交证据 → 解码正确、链上验证通过
- 正常授权 → 从链上读出实际金额 2000 mUSD、被授权方与额度均验过
- 钓鱼合约地址 → ✗ 阻止签名
- 无法解码的 calldata → ✗ 阻止签名
- 夹带 1 ETH → ✗ 阻止签名

以及完整的 连接 → 切链 → 签名 → 上链 路径（注入转发到 hardhat 的 EIP-1193 provider），链上 allowance 与页面显示一致。手机视图与浅色/深色主题均已检查，无控制台错误。

**未验证**：真实钱包（MetaMask / OKX / imToken 等）的实际行为，尤其是 `wallet_switchEthereumChain` 与 `wallet_addEthereumChain` 在各家钱包里的差异。上线前需要在真机上逐个钱包过一遍。

### 修掉的一个真 bug

初版只在页面加载时读取一次 `#` 片段。用户从 Telegram 点开**第二个**签名链接时，浏览器只改 fragment 不重载页面，于是页面继续显示上一笔交易的描述与核验结果，而 URL 里已经是新交易了——**看到的和签的不是同一个东西**。

现在 `hashchange` 会触发整页重载。用重载而不是重新渲染，是因为签名器、连接状态、已通过的核验全都是上一笔交易的上下文，任何残留都可能造成新的错位。
