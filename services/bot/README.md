# Telegram 前端

用户实际接触的界面。发起交易、入金、标记交付、确认收货、提起争议、补充证据。

## 压倒一切的设计约束：机器人不持有私钥

Telegram 担保机器人被搬空，十次有九次是因为它托管了用户密钥。所以这里**不存在**托管这个选项——不是"我们承诺不滥用"，而是代码里根本没有接收、存储或使用私钥的路径。

机器人只做三件事：读链、把操作编码成 calldata、把结果排版成消息。签名全部由用户在自己的钱包里完成。

后果是：**机器人被攻破、被关停、被封禁，用户的钱都不受影响**。每笔操作除了签名页链接，还会同时给出原始 `to` + `calldata`，任何钱包都能手工粘贴执行。你的资金不应当依赖这个机器人存活。

### 密钥粘贴防护

"我们不要"不等于"用户不会发"。用户把私钥或助记词粘进支付机器人是真实高频事故——有人分不清地址和私钥，也有人被冒充客服的骗子引导着粘贴助记词。

所以有一层主动检测（[`src/secrets.js`](src/secrets.js)）：

- 助记词按结构特征识别（连续 12 个以上的纯小写短单词），不依赖内置词表——词表会漏掉其它语言和拼写变体
- 私钥按 64 位十六进制识别。这与交易哈希形状相同，所以是**上下文感知**的：只有在提交证据的流程里才把它当作交易哈希放行
- 检测到就立即告警并给出可操作的下一步（转移资产、删除消息），且**该条消息不进入任何后续处理或存储**

日志只打 Telegram 用户 ID 和命令名，**永不打印消息内容**。状态文件只存绑定地址和流程草稿，同样不存消息原文——否则它会变成一个高价值攻击目标。

## 钱包绑定

绑定只需要地址。但光有地址不够：任何人都能声称自己是某个地址，从而窥探别人的全部交易、甚至冒充对方接收通知。

所以要证明控制权——机器人出一段带随机 nonce 的挑战文本，用户在自己钱包里签名，机器人用 `ecrecover` 验证。挑战文本里绑定了 Telegram 用户 ID 和一次性 nonce，所以签名无法被挪用到别的用户或别的绑定请求上，10 分钟过期。

挑战文本刻意写成人类可读的形式并明确声明"这不是一笔交易，不转移资产、不授予权限"——**用户越习惯于看不懂就签，越容易在真正危险的弹窗上点确认**。

## 操作可用性是合约状态机的镜像

[`availableActions()`](src/deals.js) 决定每个状态下每个角色能看到哪些按钮。这是纯函数，因为两个方向都会伤人：把不可用的操作显示成可点，用户白付一笔 gas 换 revert；把可用的操作藏起来，用户以为自己的钱卡住了。

集成测试做了**双向验证**：机器人认为可用的操作，合约 staticCall 通过；机器人隐藏的操作，合约确实拒绝。

## 防钓鱼

`/deal <地址>` 只接受工厂登记过的实例（`factory.isDeal()`）。有人发一个长得很像的合约地址骗转账，机器人会直接拦下并警告。

## 测试

```bash
npm test   # 70 项，不需要链也不需要 bot token
```

覆盖密钥粘贴防护（含上下文感知与误报检查）、绑定签名的防冒用与防重放、状态机的全部分支、输入校验，以及——

**ABI 与真实合约的一致性**：机器人手写的 ABI 逐个函数比对编译产物的选择器。这里错了，用户就会签出一笔调不通或者干错事的交易，而错误发生在他自己的钱包里，机器人看不见。

**每条通知都是合法的 MarkdownV2**：金额（`1000.0`）和 ISO 时间戳（`2026-09-14T08:08:58.000Z`）里天然含有必须转义的字符。漏一个，Telegram 不是显示错乱，而是**直接拒收整条消息**——用户什么都收不到。测试逐字符校验每条生成的通知。

## 未验证的部分

**从未真正连接过 Telegram** —— 开发环境没有 bot token。读链、状态机、编码、校验、格式化全部有测试覆盖并在真实链上验证过；Bot API 的收发（长轮询、MarkdownV2 渲染、行内键盘回调）是照官方 API 文档写的，未经真实连接验证。

首次部署时建议：先用一个测试群和测试网合约跑通 `/start → /bind → /new → 入金 → 确认收货` 全流程，再接主网。

## 事件推送与到期提醒

[`src/watcher.js`](src/watcher.js)。两类通知性质完全不同：

**事件通知**（对方入金了、卖家发货了、裁决下来了）纯粹是体验问题。

**到期提醒**不是锦上添花——**验收期届满买家还没动作，货款就自动放给卖家了**。一个不知道这件事的买家会因为「没看手机」而实际损失。所以提醒只发给「不作为会吃亏」的那一方，并明确说清后果。档位是 24h / 6h / 1h，每档每笔只发一次。

两处工程细节：

- **等确认数再推**（默认 5 块）。通知内容是「钱到账了」这类不可撤回的判断，重组后一条已推送的「对方已入金」会变成假消息，而用户可能已经据此发了货。
- **去重键用 `txHash + logIndex`**，同一条日志无论被扫到几次都只推一次。重启后从状态文件恢复，不会重发历史通知。

## 信誉展示

[`src/reputation.js`](src/reputation.js) + [`src/repcommands.js`](src/repcommands.js)。可选层：没配 `REPUTATION` / `IDENTITY_BOND` 时 `/rep` `/bond` `/unbond` `/record` 只回一句「未接入」，担保交易功能完全不受影响。

**不给星级。** 星级会让人把「4.8 星」当成一个可以直接相信的结论，但它压缩掉了唯一重要的信息——具体到这一笔交易，对方骗你能赚多少、要付出什么。同样的「4.8 星」在 100 块和 10 万块的交易里含义完全不同。

所以 `/deal` 里展示的是针对当前这笔交易的一个数：

```
机制缺口 = 货款 − 对方在这笔交易里的保证金
```

缺口 ≤ 0 → 绿色，**与对方是谁无关**。缺口 > 0 时才轮到身份押金去覆盖，而这时给出的建议是「把对方的保证金提到不低于货款」，**不是「相信这个人」**——一个把用户导向「信任一个陌生人」的评估，比没有评估更危险。

两处容易出错的地方，都有测试守着：

- **押金正在撤回时按 0 计**。它还在合约里，但公示期一到就会被取走，而你的交易可能还没结束。不能依赖的钱不算数。
- **刚押入的身份不能显示成「年龄 无」**。合约的 `ageOf()` 在「没押金」和「这一秒刚押的」两种情况下都返回 0，直接渲染会出现「年龄 无 / 押金 500」这种自相矛盾的一行。
