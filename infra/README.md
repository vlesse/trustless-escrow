# 测试网上跑起来的东西

装法：把 `*.service` / `*.timer` 拷到 `/etc/systemd/system/`，
`reveal-try.sh` 拷到 `/srv/escrow/`，然后 `systemctl daemon-reload`。

## escrow-keeper.service

常驻。推进协议里那些「任何人都可以做、但没人会主动做」的步骤：
抽签、开揭示、计票、结案、沉淀信誉记录。

这把钥匙能做的每件事合约上任何人都能做，它碰不到资金也没有管理员权限，
所以可以热放在机器上。但**不要和提案人的钥匙（要质押、会被罚没）或
管理员的钥匙（能停新单）共用** —— 三者的风险等级完全不同。

`POLL_INTERVAL_MS` 和链的出块速度绑死，不是性能参数。`blockhash` 只能
回溯 256 个区块，BSC 上 256 块只有约 115 秒。轮询慢于这个窗口，抽选会
反复过期重排，案件一路耗到超时以拒裁收场，**而两边都不会有任何报错**。
启动时会按链上实际出块速度核一遍，太长直接拒绝启动。

## escrow-reveal.timer

每 30 分钟试一次陪审员揭示。揭示窗口只有 2 天，错过的席位被当作弃权
并罚没质押 —— 人不可能守在那里等，所以这一步必须自动化。
脚本幂等，阶段不对就静默退出。

这只是模拟场景用的。真实陪审员的揭示由他们自己负责。

## escrow-bot.service

Telegram 前端。长轮询,不需要开入站端口。

机器人**永远不接触私钥**:它只构造 calldata,把签名链接发给用户,
签名在用户自己的钱包里完成。所以这个进程里没有任何值钱的东西。

`CONFIRMATIONS=5`:推送内容是「钱到账了」这类不可撤回的判断,重组之后
已推送的消息会变成假消息,而用户可能已经据此发了货。

## nginx-escrow-signing.conf

签名页的静态托管(`https://db.renrenyings.net`)。证书由 certbot 签发,
配置里的 443 段和跳转是 certbot 自己加的。

页面是纯静态的:没有后端、没有数据库、不收集任何东西,连 ethers 都是
本地 vendored 的而不是走 CDN —— 一个负责核对签名目标的页面,不该把
自己的完整性交给第三方脚本。

`config.js` 单独设了 `no-store`:它是部署方唯一要改的文件,缓存住旧的
合约地址会让页面拿错误的锚点去校验。

## escrow-backup.timer

每天备份「只存在于这台机器上」的东西。代码在 GitHub 上不用备,真正丢不起的是:
角色私钥、各服务的 .env(含机器人 token)、Telegram 账号与钱包地址的绑定关系、
陪审员投票的 salt(丢了那几席就永远揭示不了、质押被罚没)、以及哪套合约在服务。

它还会每天 `git status` 一遍,有未提交的改动就单独存一份 patch 并在日志里喊一声。

这条是被真事逼出来的:2026-09-29 的检查发现,**一整周的漏洞修复只存在于这台机器上**,
从来没提交过。机器一挂就全没了,而当时没有任何机制会告诉我们这件事。

备份落在 `/srv/escrow-backups`(700),保留 30 份。
**注意它和被备份的数据在同一台机器上** —— 这挡得住误删和手滑,挡不住机器整台没了。
要挡后者,得把归档定期拉到别处。
